# B7: Judge and Phase A Calibration Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Meet plan §9 B7: "v1 and v2 judge; agreement per dimension with intervals; ≥80% in each". Build MP1's Step 4 (the LLM judge) and the Phase A half of Step 6 (judge calibration on the baseline items, before Phase B). The tooling covers six parts:
- a judge run with bounded, audited and resumable attempts;
- a qualification receipt that pins the judge model and records why it may judge;
- an acceptance policy and a calibration report: exact per-dimension agreement, confusion counts, TPR and TNR, each with a 95% Clopper–Pearson interval;
- a pool of development-split disagreements from which judge v2 draws its few-shot examples by similarity;
- a frozen-judge receipt for the Phase B comparison;
- the judge and calibration commands.

No test or assistant calls a model. Every model run (the development collection, the smoke judge run and each measured judge run) needs Chad's go-ahead and servers that are already reachable. B7's acceptance is met only when the measured runs are done and the calibration report says so.

**Architecture:** Port `judge`, `qualification`, `acceptance` and `calibration` and the judge and calibration commands of `evaluation_cli` from the earlier repository (PORTING-MAP §3.3, §3.5, §8 B7), as behaviour-tested rewrites on B6's `assessment`, `labels`, `human_reference` and `evaluation_schemas`. Three modules are new: `judge_examples` (PORTING-MAP §4 item 9), `judge_config` (Decision 1) and `display` (B6's escaping helper, moved; Interfaces with B6). Four changes of design:
1. The judge is blind in the same way Chad is. It sees what Chad's display shows, plus the recorded deterministic check results. It never sees a run id, item id, arm, prompt variant, model or any human label.
2. Judging needs a frozen human reference, so no judge evidence can exist before the labels are frozen. The only exception is a smoke run, which is allowed only on a development assessment that will never be labeled.
3. Judge v2's examples come only from development-split disagreements. v2's prompt and example pool are frozen and recorded before any judge result on the baseline reference is read.
4. A human decision left unresolved, or a judge decision that is missing, counts against agreement. It is reported and never treated as a match.

**Tech Stack:** Python ≥3.12, Pydantic 2, Instructor 1.17+, OpenAI SDK 2 (local OpenAI-compatible endpoint), httpx, pytest, ruff. No new dependency.

**Spec:** `docs/MP1-BONSAI-HELP-CHATBOT.md` (§6.2–§6.4, §7 Steps 4–6, §8 Models, §9 B7), `AGENTS.md` (Judge, Models, Credentials, Criteria, No fabrication, Human labels, Iteration), `docs/PORTING-MAP.md` (§3.3 rows `judge`, `qualification`, `calibration`, `acceptance`; §3.4 `compare_human`/`stats`; §3.5 `evaluation_cli`; §4 items 9 and 18; §8 B7), `docs/DECISIONS.md` (November 24, 2026: B5 entries, "rubric accepted", "B5 report and gate freeze"), and the B6 plan `docs/superpowers/plans/2026-11-24-b6-labels.md` (Decisions 5, 8, 13 and "Obligation for B7"). ## Global Constraints

- **The judge is independent.** It has a separate prompt (`prompts/judge-v1.md`, later `judge-v2.md`) and runs at a lower temperature than every generator collection it judges. The generator's temperature is read from each source collection's recorded settings (0.6 for the baseline), never typed. The output is Instructor/Pydantic `evaluation_schemas.Judgment`: six binary decisions, each with a nonblank reason. The prompt version (file stem) and SHA-256 are recorded in the run identity.
- **Assessed use needs a distinct judge.** A measured run refuses a judge whose `model`, `model_identity` or `model_sha256` equals any source generator's. A reply that reports another model id, or the generator's, is an attempt failure (`ModelIdentityMismatch`), and it blocks calibration. Same-model smoke judging is diagnostic only. Diagnostic agreement never counts as calibration.
- **No judge evidence before frozen labels.** A measured judge run calls `human_reference.load_reference` first. Without a frozen reference it refuses before any directory is created or any call is made (B6's obligation for B7). A smoke run is refused on an `arm` assessment.
- **Blind inputs.** The judge sees each item's category, setup record (Blender and Bonsai versions, IFC schema, discipline, model state; no setup id), seven fields, the model's quotes, the full text of its cited sections, and the recorded deterministic check results. It sees no run id, item id, trace id, arm, prompt variant, prompt hash, generator model, generation time, collection or cohort id, human label or note, and no other judge output. All item, quote, section and check text is enclosed in blocks whose boundary item text cannot forge (Decision 4).
- **Attempts are persisted like generation.**
  - A durable start record is written before each call.
  - Every completion is persisted with its raw response, whether valid or not, and including malformed output, schema-invalid output and typed transport failures.
  - A start without a completion is an unknown outcome. It uses up its attempt and is disclosed.
  - The number of attempts per item is bounded. Exhaustion is a controlled failure with exit code 3, never a traceback or an infinite loop.
  - A resume keeps the original settings, prompt, examples, code and reference, and gives exhausted items no extra attempts.
- **Immutability.** Judge runs, qualification receipts, example pools, calibration reports and frozen-judge receipts are written once and never overwritten. Every new experiment gets a new id. Assessments, labels, references, cohorts, collections and runs are read, never written.
- **Thresholds come from the pinned rubric.** That covers the per-dimension agreement minimum (`thresholds.human_judge_agreement.per_dimension_minimum`, 0.8, inclusive, Phase A before Phase B), the dimension ids and the interval confidence. Nothing is hard-coded a second time.
- **Development and assessed stay apart.** Judge v2's rules and examples come only from development-split disagreements. Nothing from an `arm` assessment (item text, judge reasons, per-item disagreements) enters a judge prompt or example pool. Assessed items are never v2 examples. A calibration report keeps its per-item disagreements in a separate file (Decision 16), and whoever writes a later judge prompt reads only the per-dimension figures of an `arm` report.
- **Models and credentials.** Local endpoints only, under the same endpoint and credential rules as `RunConfig`: one credential source, values never in config, prompts, arguments, logs or manifests, and `hosted: true` refused at load. The client never discovers or starts a model.
- **Never fabricate.** No human label, judge decision, agreement figure, model measurement or approval is invented. A pending check is not a pass, a missing judgment is unresolved, and a dimension below 80% is reported as measured.
- **The gate stays frozen.** `checks.py`, `gate.py` and `sampler.py` are not edited. The judge reads the gate's recorded check results through the collection's verified gate reports and never re-runs or changes a check.
- **Tests exercise behaviour.** Synthetic assessments, labels and references go under `tmp_path`, built with B6's `tests/evaluation_support.py`. Transports are faked with `httpx.MockTransport` and `tests/fakes.py`. Documentation text comes from the committed fixture slice. Every synthetic reviewer string is visibly synthetic. No skip, xfail, TODO or stub.
- **Verification for every task:** `uv lock --check`, `uv run --locked pytest -q`, `uv run --locked ruff check .`, `uv run --locked ruff format --check .`.
- **No commit or staging in this workflow.** Commits happen only when Chad asks; the "commit" lines below name the intended message for that time.

## Decisions this plan makes (assistant's calls, recorded in DECISIONS.md in Task 9)

1. **A separate `JudgeConfig`.** It lives in a new module, `judge_config.py`, with `load_judge_prompt`, and imports the endpoint and credential helpers from `config.py`. It is not in `config.py` itself, because the frozen judge (Decision 13) pins the code that renders the judge's messages, and B8 may still need to change `RunConfig`. It does not subclass `RunConfig`, whose generation fields (`split`, `prompt_variant`, `seed`) mean nothing to a judge. Its fields:
   - `base_url`, `model`, `model_identity`, `model_sha256` (both required when `purpose` is `measured`);
   - `purpose: Literal["smoke", "measured"]`;
   - `prompt_path` (default `prompts/judge-v1.md`), `mode` (`json` | `tools`);
   - `temperature` (default 0.0; must be below every source generator's temperature), `enable_thinking: bool | None` (default None, which sends nothing);
   - `timeout_seconds` (default 300, at most 600), `max_tokens` (default 1500), `max_attempts` (default 2, at most 3);
   - `api_key_env` / `api_key_file` (exactly one);
   - `embedding_base_url`, `embedding_model`, `embedding_api_key_env` / `embedding_api_key_file` (v2 only);
   - `examples_k` (default 4, 1 to 6; v2 only);
   - `artifact_root` (default `runs`), and `hosted` (refused when true).

   `public_settings()` leaves out every credential name and path, as `RunConfig` does. The timeout ceiling is higher than the generator's 300 s because a 70B model on local hardware is slow; it is still bounded (Open question 2).
2. **Prompt version and placeholders.** The prompt version is the file stem (`judge-v1`). The identity records the stem and the file's SHA-256, and the run directory holds a copy of the prompt. `load_judge_prompt` requires exactly `{category}`, `{setup}`, `{item}`, `{quotes}`, `{sections}`, `{checks}` and `{fence}` (Decision 4), plus `{examples}` if and only if the run has an example pool. Any other placeholder is refused. The rendered prompt is the system message. The user message is fixed: `Judge the item above, attempt N of M. Reply with the JSON object only.`
3. **v1 is criteria and labeling rules only.** `prompts/judge-v1.md` holds the accepted rubric's five labeling rules and, for D1 to D6, the pass and fail anchors and every labeling note (check, common fail patterns, borderline), copied verbatim from `config/rubric.json`. It adds a short section, "How these rules apply to you", that maps three instructions written for a human onto the judge's evidence:
   - there are no pinned pages beyond the cited sections, so a typical hazard counts for D2 only when the cited sections confirm it;
   - how a name is confirmed as "known" to exist, stated to match what the frozen checks actually report (`checks.py` at `3b3c51e`):
     - A name the cited sections show is confirmed, and must match them.
     - A `bim.` operator id in tools_required or steps is confirmed to exist when `bim_operators_known` passed, because that check compares every `bim.` id in those two fields with the operators registered in the add-on source pinned for the version line. Its detail is only a count (`N ids checked`), it does not read the answer field, and it confirms no panel, menu, button, setting or hotkey.
     - `blender_operators_known` and `menu_paths_known` are evidence only (`checks.EVIDENCE_ONLY`) and never confirm a name. Their pass detail is `ok` with no names, and `ok` also results when nothing was examined: the first looks only at dotted operator ids in tools_required and steps (never the answer), and only those whose prefix is a Blender operator prefix in the Manual lexicon for the version line; the second looks only at `>`- or arrow-style paths in steps. The menu check matches each segment on its own against a broad label set, so real labels in a wrong combination still pass.
     - Every other operator, panel, menu path, setting and hotkey is confirmed only by the cited sections. Otherwise it is unconfirmed and D3 decides 0, as the rubric's D3 borderline ruling already says.
     - Memory never confirms a name; it only prompts a closer look.
   - the judge cannot record unresolved: when it cannot confirm a pass it decides 0 and says what could not be confirmed.

   The `bim_operators_known` sub-rule is the only place a check confirms anything, and it confirms only what the pinned add-on source shows, that the id is a registered operator; the prompt keeps "a passed check never makes a dimension pass". A considered alternative was to have `render_inputs` list the exact names each lexicon check examined. It was not chosen, because it would re-implement the frozen gate's extraction outside the gate, where the two could drift apart; the prompt instead states each check's coverage, and a test pins the premises (Task 1). If Chad prefers that only the cited sections confirm a name, the `bim_operators_known` sub-rule is dropped before v1's hash is pinned (Open question 4).

   The prompt has no few-shot examples. Its draft asks for the reason before the decision in each dimension, and its JSON template puts `reason` first. That order holds only if the response schema declares `reason` before `decision`: in Instructor's `tools` mode, and usually in `json` mode, the model follows the schema's property order. B6's `DimensionJudgment` currently declares `decision` first, so the draft and the schema disagree. The order is settled with B6 before v1's hash is pinned, and the prompt then matches the schema either way:
   - If B6 declares `reason` first (B7's request, Interfaces with B6), the draft stands.
   - If B6 keeps `decision` first, the prompt's "Your reply" paragraph and JSON template are changed to put `decision` first, and the prompt no longer asks for the reason first. v1's iteration-log entry records that the reason-first order was dropped to match the schema.

   `test_judge_prompt_template_matches_schema_order` (Task 1) fails while they disagree, so the hash cannot be pinned on a contradiction. A drift test fails if any rubric string is missing from the prompt.
4. **What the judge sees.**
   - **Same as Chad's display.** The item's category, its setup record, its seven fields, the model's quotes and the full text of its cited sections, re-derived from the hash-verified fixture slice by `sampler.section_texts`. Control characters are escaped with B6's display escaping (`display.escape_control`, Interfaces with B6).
   - **Added for the judge: the deterministic check results.** These are the `CheckResult` records the gate recorded for the item, read from the verified gate report. Plan §7 Step 4 lists them as judge input, so the judge sees them although Chad's display does not.
   - **Exact format.** `render_inputs` returns these placeholder values, and the prompt's "The item" section describes exactly this format:
     - `{fence}`: a 16-hex code, the first 16 characters of the SHA-256 of the canonical JSON of `{"domain": "bonsai-judge-fence-v1", "category", "setup", "item", "quotes", "sections", "checks"}` (the unfenced values). The code depends on the item's own text, so item text cannot contain the code of the message it appears in; the domain string keeps it distinct from every payload and trace hash. If the code occurs in any block's text anyway, `render_inputs` raises `JudgeError` and the attempt is not started.
     - `{category}`: the category id. `{setup}`: exactly five lines, in this order, joined by single line breaks, with no indent, no blank line and no trailing line break: `Blender: <blender>`, `Bonsai: <bonsai>`, `IFC schema: <ifc_schema>`, `Discipline: <discipline>`, `Model state: <model_state>`. The labels and order are B6's display's, but the layout is not: B6 indents the five lines four spaces under a `Setup:` line, while the judge prompt supplies its own `Setup record:` line and the five lines start at the left margin. Both values come from the assessment's own records, not model text, and are escaped but not fenced.
     - `{item}`: one block, `<<<BEGIN {fence} ITEM>>>` … `<<<END {fence} ITEM>>>`. Inside it, the field headings `Question:`, `Answer:`, `Equipment problem:`, `Tools required:`, `Steps:`, `Safety info:` and `Tips:` start a line, and each field's text is indented by four spaces (`- ` before each tool and tip, `N. ` before each step), as in B6's display. A heading-like line inside a field is therefore indented and cannot pass for a field heading.
     - `{quotes}`: one block named `QUOTES`, one quote per line as `[<section id>] <text>`, with each line break in the text shown as `\n`, so a quote cannot start a second line with another section id.
     - `{sections}`: one block per cited section, in citation order, named `SECTION <section id>`. Each holds `Source: …`, `Path: …` and `Heading: …` lines (as in B6's display, with B6's heading rule, `display.section_heading`), then the section's full text exactly as `sampler.section_texts` gives it, after escaping. B6's `--- id ---` / `--- end of id ---` delimiters are not used for the judge, because a line of item or section text can imitate them.
     - `{checks}`: one block named `CHECKS`, one line per recorded check as `<dimension> <name>: passed (<detail>)` or `… failed (<detail>)`, in the gate's recorded order, with any line break in a detail shown as `\n` (a detail can quote item text).
     - Every block boundary line stands alone on its line.
   - **Reading the key.** The judge reads B6's `key.json` (`assessment.load_key`) only to find each item's run and gate record. Nothing from the key reaches a message. Whether the judge should see the category and quotes at all is Open question 3.
5. **Run layout.** A judge run lives at `<assessment dir>/judges/<judge_run_id>/` and holds:
   - `manifest.json`: identity, fingerprint, status and artifact hashes, checkpointed atomically;
   - `prompt.md` (a copy of the prompt);
   - `starts.jsonl` and `attempts.jsonl`;
   - for v2, `examples.json`, holding the pool copy and the selection.

   The identity covers the public settings, the prompt stem and SHA-256, the assessment SHA-256, the reference SHA-256 (measured runs), the qualification SHA-256 (measured runs), the example pool SHA-256 and `examples_k` (v2), the source generators' recorded temperatures and model hashes, and the implementation identity. Attempt ids are `<judge_run_id>:<blind_id>:<n>`. B6's `freeze_reference` refuses when `judges/` exists, which is how a smoke run blocks a later freeze.
6. **Budgets.** Each item gets `max_attempts` attempts (default 2, at most 3); a resume gives an exhausted item no more. An assessment allows at most 3 measured judge runs (distinct judge run ids). On the B6 baseline reference these are v1 and v2, plus one spare that needs Chad's decision. A further run is refused. The cap guards against tuning the judge prompt on the assessed reference by repeated tries.
7. **Qualification.** `judge-qualify` writes a receipt to `runs/judge-qualifications/<id>.json`. It records:
   - the judge's public settings, `model_identity` and `model_sha256` (under git-ignored `runs/` only);
   - the basis `distinct_model`, with the decision reference "DECISIONS.md, November 24, 2026: judge model";
   - evidence: a complete smoke judge run with the same model and settings (any prompt), in which every reply reported the configured model id.

   A measured run refuses a missing receipt or one that does not match its config. It also refuses a judge that matches any source generator by `model`, `model_identity` or `model_sha256`. PORTING-MAP's same-model basis (same model, different prompt, lower temperature) is not built, because Chad chose a distinct model; adding it later is a new dated entry.
8. **Agreement.** Per dimension, over every selected blind id `n`:
   - `matching` counts the items where the human decision (0 or 1) equals the judge decision.
   - `agreement = matching / n`. A human `None` (unresolved) or a missing judge decision (exhausted item) is in `n` and never matches. Both are counted and reported (`human_unresolved`, `judge_missing`).
   - Confusion counts are over the pairs where both decisions exist (`h1_j1`, `h1_j0`, `h0_j1`, `h0_j0`).
   - TPR is `h1_j1 / (h1_j1 + h1_j0)`: of the items the human passed, the share the judge passed. TNR is `h0_j0 / (h0_j0 + h0_j1)`: of the items the human failed, the share the judge failed.
   - Agreement, TPR and TNR each carry a 95% `stats.clopper_pearson` interval. A zero denominator is undefined (null), never 0 or 1.
   - A dimension meets the minimum when `matching / n ≥ 0.8`, compared exactly as fractions on the point estimate, with the interval reported beside it (24 of 30 meets the minimum; 23 of 30 does not).
   - Per-category agreement is reported without a threshold.
9. **Readiness (Phase A met).** A calibration report is `ready` only if all of these hold. Otherwise it is `pending` with every reason listed.
   - The assessment is kind `arm`.
   - The reference is frozen and verified, and labels amended after the freeze are not used (`load_reference`).
   - The judge run is `measured` and complete: every selected blind id has a valid judgment.
   - The qualification is valid, and every reply reported the configured judge model.
   - The judge temperature is below every source generator's.
   - The rubric pin equals the reference's.
   - Every dimension meets the minimum.

   A development assessment or a smoke run gives status `diagnostic`, whatever its agreement. `judge-freeze` accepts only a `ready` report.

   **Unknown outcomes are disclosed, not blocking.** An unknown outcome (a start with no completion, for example after a hard kill) uses up its attempt, as `AGENTS.md` requires, and the report lists its count and attempt ids beside the figures. It does not by itself make the report `pending`. The run is resumed under its own id, which is not a new measured run, so it does not use up the spare in Decision 6. Each item's remaining attempts then run. An item whose attempts are all used up without a valid judgment leaves the run `incomplete`, and that item counts against agreement (Decision 8), so the report is `pending`. The reason for not blocking: an unknown outcome's reply was never read by anyone, so it cannot be used to choose among judgments, and blocking would let one hard kill in a run of several hours spend a measured run that has a valid judgment for every item.
10. **Example pool for v2.** `judge-examples` builds `runs/judge-examples/<pool_id>/pool.json` from one development assessment:
    - The assessment must be kind `development`, with its reference frozen and a complete measured judge v1 run on it. An `arm` assessment is refused.
    - The entries are the (blind id, dimension) pairs where Chad's resolved decision differs from the judge's. Each holds the item's category, setup, seven fields, that dimension's check lines, Chad's decision and the rubric anchor for it (the pass anchor for 1, the fail anchor for 0).
    - No note and no judge reason enters the pool. The judge's wrong reason is not shown as an example.
    - One vector per item is stored, embedding `question + "\n" + answer` with the gate's embedding model. A different model is refused, under the one-embedding-model rule.
    - The pool is sealed by SHA-256 and records its source assessment, reference, judge run and embedding model.
11. **Selection by similarity.**
    - **When it happens.** For a v2 run, every judged item's vector is computed when the run is created, before any chat call, and the selection is written into the run's `examples.json`. An embedding failure therefore creates no run and no start record.
    - **How entries are chosen.** For each judged item, the `examples_k` nearest pool entries by cosine similarity are taken, ties broken by entry id.
    - **What is recorded.** Each start record lists its `example_ids`.
    - **What is refused.** A run is refused when the pool shares a trace id or payload hash with the judged assessment, or when the pool comes from a non-development source.
12. **Judge v2 is pre-registered.** `prompts/judge-v2.md` is v1 plus two additions:
    - a "Rules from development disagreements" section;
    - an `{examples}` placeholder, rendered from the selected entries.

    The assistant writes each rule from a pattern of at least two development disagreements in the same dimension and the same direction. Each rule names the rubric note it applies and never changes the rubric's meaning; a change of meaning is a new rubric version, which is Chad's decision.

    Before any judge result on the baseline reference is read, a dated DECISIONS.md entry records the v2 SHA-256, the pool SHA-256 and `examples_k`, together with the selection rule in Decision 13. That entry also serves as v2's iteration-log record: date, change, hypothesis, before (v1's development agreement per dimension), and after (filled in once the baseline runs are done). v2 is not scored on the development assessment, whose disagreements are its examples.
13. **Which judge is frozen.** This rule is pre-registered with Decision 12. After v1 and v2 have each run once on the B6 baseline reference:
    - the frozen judge is v2 if its report is `ready`;
    - otherwise it is v1 if v1's report is `ready`;
    - otherwise Phase A is not met. That is reported as measured, and the next step is Chad's decision (Open question 7).

    If Phase A is not met and Chad chooses to carry a judge forward to B8 anyway (Open question 7(c)), the judge carried forward is chosen by this pre-registered rule, among the measured runs on the baseline reference: the report with more dimensions at or above the minimum; then the higher minimum per-dimension agreement; then the later prompt version. B7 does not build a freeze for that case, because `judge-freeze` accepts only a `ready` report and B8 judges only with `--frozen-judge`. Option (c) therefore needs its own dated decision from Chad and a small, separately recorded addition: `judge-freeze --phase-a-not-met --decision-ref TEXT`, which writes a selection receipt with basis status `pending`, every reason the report gives, and the decision reference. `--frozen-judge` then accepts that receipt, and every B8 report made with it states that Phase A was not met. That addition is built only if Chad chooses (c), as a dated DECISIONS.md entry.

    `judge-freeze` writes `runs/judge-selections/<id>.json` with the report SHA-256 and the frozen judge identity (`judge.frozen_identity`). A later measured run that passes `--frozen-judge <id>` (B8's mixed assessment) must match the frozen identity exactly. The frozen identity holds:
    - the judge's public settings, `model_identity` and `model_sha256`, the prompt stem and SHA-256, and for v2 the pool SHA-256 and `examples_k`;
    - per-file SHA-256 of every module in `judge.FROZEN_JUDGE_MODULES`, the modules that can change the text the judge sees or how its reply is parsed;
    - `dependencies`: the installed version, read with `importlib.metadata.version`, of every distribution in `judge.MESSAGE_PATH_DISTRIBUTIONS`, the third-party libraries that build the judge's request or parse its reply. Each is listed with its reason:
      - `instructor`: builds the request from `Judgment` (in `json` mode it writes the schema, in its own wording, into the system message; in `tools` mode it sends the schema as a tool definition) and parses the reply;
      - `openai`: the SDK that builds and sends the chat request and decodes the response;
      - `pydantic`: generates `Judgment.model_json_schema()` and validates the reply;
      - `pydantic-core`: the validation and schema core under `pydantic`;
      - `httpx`: the transport that carries the request body and reads the reply;
      - `jiter`: the JSON parser that the OpenAI SDK and Instructor import for reply parsing.

      `frozen_identity` cross-checks each installed version against the `uv.lock` entry for the same package. A distribution that is missing, absent from `uv.lock`, or installed at a version other than the locked one makes `frozen_identity` raise `JudgeError`, so freezing and every `--frozen-judge` match refuse it;
    - `judgment_schema_sha256`: the SHA-256 of the canonical JSON of `Judgment.model_json_schema()`, so a Pydantic change that alters the schema is caught even when the version strings look unchanged.

    A `--frozen-judge` match requires `dependencies` and `judgment_schema_sha256` to equal the frozen values exactly. A change to any other locked package (one B9 adds for its charts, for example) does not affect the match. A re-lock that changes the version of a listed distribution is a dated DECISIONS.md entry, after which the judge is no longer the frozen one for the comparison.

    **The list is the import closure.** `judge.render_path_closure(package_dir=None) -> set[str]` reads every module of the package by AST and follows every `bonsai_help` import (module level and inside functions; `from bonsai_help import x`, `from bonsai_help.x import …`, `import bonsai_help.x` and relative imports). It starts from `judge`, `judge_config`, `judge_examples` and every module in `FROZEN_JUDGE_MODULES`, and it follows the imports of exempt modules too, so nothing is reached through an exemption without being listed. ## Order of operations (Chad's steps are marked **Chad**)

An assistant never runs `label` or `freeze-human-reference` and never writes a label. Every model run needs Chad's go-ahead and servers that are already reachable.

1. **B6 first.** **Chad** labels the 30-item baseline assessment in his own terminal and freezes it (`freeze-human-reference --declare-blind`). Nothing in B7 judges it before then, and the code refuses to.
2. **Judge server.** **Chad** serves the judge model locally and writes `config/judge.local.json` (git-ignored) from `config/judge.example.json`, with `model`, `model_identity` and `model_sha256` set. The file name and hash stay in that file. The assistant checks the config with `judge --help` and a load test, never with a call.
3. **Development collection** (Chad's go-ahead). This is a new config with `purpose: "baseline"`, `prompt_variant: "baseline"` and `split: "development"`. Everything else is exactly the baseline's: `prompt_path: "prompts/generator-v1.1.md"`, temperature 0.6, `enable_thinking: false`, the same model and hash, and the same embedding model and server. Run `collect` under a new collection id, for example `development-b7-1`, with the default policy (batches of 70, at most 3, at least 50 retained with at least 10 per category); exit 3 is reported, and the budget is not raised. Then run `cohort` (50 items, 10 per category) as, for example, `development-b7-cohort-1`. The baseline's figures are untouched: the development collection never enters an arm's denominator. `collection-report` gives its three figures with intervals.
4. **Smoke assessment and smoke judge** (Chad's go-ahead). The assistant runs `assessment create --cohort development-b7-cohort-1 --count 5` as `dev-judge-smoke` (kind `development`, never labeled), then `judge` with `purpose: "smoke"` and judge v1. This shows that the judge answers in the schema and reports its model id. It is diagnostic only, and B6's freeze code will refuse this assessment from then on.
5. **Qualification.** The assistant runs `judge-qualify` with the smoke run as evidence. This step makes no model call.
6. **Development labels.** The assistant runs `assessment create --cohort development-b7-cohort-1 --count 20 --exclude-assessment dev-judge-smoke` as `dev-labels-1`, which gives 4 per category. **Chad** labels it and freezes it (`--declare-blind`). Its labels never enter an arm's denominator or the Phase A agreement.
7. **Judge v1 on the development reference** (Chad's go-ahead). This is a measured run on `dev-labels-1`. Then `calibrate` writes a `diagnostic` report: v1's development agreement and disagreements. It exits 0 and prints `status: diagnostic (never calibration)`; that is the expected result here, not a refusal.
8. **Example pool.** The assistant runs `judge-examples` on `dev-labels-1` and the v1 run. This step needs the embedding server only.
9. **Write and pre-register judge v2.** The assistant writes `prompts/judge-v2.md` from patterns in the development disagreements (Decision 12). It records the v2 SHA-256, the pool SHA-256, `examples_k` and the selection rule (Decision 13) in a dated DECISIONS.md entry, which is also the iteration-log record. Until this entry exists, no measured run is made on the baseline assessment.
10. **Phase A on the baseline reference** (Chad's go-ahead). The assistant runs judge v1 and then judge v2 (with `--examples`) once each on the B6 baseline assessment, then `calibrate` for each. The reports give per-dimension agreement, confusion counts, TPR and TNR with intervals. The assistant reads the main reports only, not their disagreements files (Decision 16). A run stopped by a hard kill is resumed under its own id; its unknown outcomes are disclosed (Decision 9). With 30 items an interval is wide (24 of 30 is 80%, with a 95% interval of about 61% to 92%); that is reported, not hidden.
11. **Freeze the judge.** Under the pre-registered rule, `judge-freeze` on the chosen `ready` report. If neither report is `ready`, Phase A is not met and no judge is frozen. That is reported honestly, and Chad decides the next step (Open question 7); option (c) needs his dated decision and the `--phase-a-not-met` addition first (Decision 13). Nothing is re-run quietly, and no threshold moves without a dated amendment.
12. **Hand-off to B8.** B8's mixed assessment is judged only after its reference is frozen, with `--frozen-judge`. B8 changes no module in `FROZEN_JUDGE_MODULES` (Decision 13). While B8's labels are pending, Chad does not open the B6 reports' disagreements files (Open question 6).

## Open questions for Chad (recorded in DECISIONS.md in Task 9)

1. **Judge temperature.** It must be below the generator's 0.6. Recommended: 0.0, so the judge is as repeatable as the server allows and re-judging the same item gives the same decisions. The alternative is 0.1, the earlier repository's default, which may vary slightly between runs. The value is part of the frozen judge, so B8 uses it too.
2. **Serving the 70B judge.** Which local server and quantization, and which context window? A v1 request is about 6,000 to 7,000 tokens: about 3,200 tokens of prompt, up to about 1,800 of sections, the item, the check results, and up to 1,500 for the output. A v2 request with 4 examples is about 10,000 tokens. Recommended: a context of at least 16k tokens (32k for margin), `max_tokens` 1500 and `timeout_seconds` 300, raised to at most 600 if the server is slower. A judge run of 30 items at 2 attempts at most is then a matter of hours, not days. Also, should `enable_thinking` stay unset (None, which sends nothing)? That is recommended for a model that is not a thinking model.
3. **Does the judge see the category and the model's quotes, as Chad's display does?** Recommended: yes. The judge then sees what Chad saw, plus the check results that plan §7 Step 4 adds. Leaving them out would make the judge's evidence differ from the labeler's. v1's placeholders include both, and the answer is settled before v1's hash is pinned.
4. **The three adaptations in "How these rules apply to you" (Decision 3).**
   - Only the cited sections confirm a typical D2 hazard, because the judge has no other pages.
   - How a name is confirmed for D3. What the frozen checks actually report:
     - `bim_operators_known` compares every `bim.` id in tools_required and steps (not the answer) with the operators registered in the pinned add-on source for the version line. Its pass detail is only a count (`N ids checked`).
     - `blender_operators_known` and `menu_paths_known` are evidence only. Their pass detail is `ok`, which also results when nothing was examined (no dotted id with a Blender operator prefix from the Manual lexicon in tools_required or steps, the answer never being read; no `>`-style path in steps). The menu check matches each segment on its own, so real labels in a wrong combination pass.
     - No check covers panel names written without a path, settings, button labels or hotkeys.

     The draft therefore says: a name the cited sections show is confirmed; a `bim.` id in tools_required or steps is confirmed to exist when `bim_operators_known` passed (the judge finds the ids itself, since the check lists none), but that confirms no panel, menu, setting or hotkey; the other two checks never confirm a name; every other name is confirmed only by the cited sections, or it is unconfirmed and D3 decides 0; memory never confirms a name (Llama 3.3's training predates Blender 5.2 and Bonsai 0.9).

     Recommended: keep this. The alternative is stricter: only the cited sections confirm any name, `bim.` ids included. That would fail D3 on every item whose `bim.` operator the cited sections do not show, even though the pinned source registers it.
   - Decide 0 when a pass cannot be confirmed.

   Do these keep the meaning of your accepted rubric? If any one changes it, the alternative is a new rubric version.

   A related point: for D2, your labeling allows a pinned docs page outside the cited sections, which the judge cannot see. That is a likely source of D2 disagreement. Do you want a fixed, cited set of hazard pages added to the judge's input in v2? Recommended: decide after the development disagreements show whether this matters.
5. **Unresolved decisions in agreement.** Recommended (Decision 8): a human `u` or a missing judge decision counts in the denominator and never matches. This is conservative: a dimension with 7 unresolved items out of 30 cannot reach 80%. The alternative is to leave them out of the denominator and report them, which the rubric's "unresolved, never a pass" argues against.
6. **What you read before B8.** Each B6 calibration report keeps its per-item judge reasons in a separate disagreements file (Decision 16). Reading them before labeling B8's mixed queue could pull your later labels toward the judge. Recommended: read the main reports (per-dimension figures) only, and the disagreements files after B8's reference is frozen.
