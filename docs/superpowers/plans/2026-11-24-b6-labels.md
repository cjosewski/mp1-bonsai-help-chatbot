# B6: Blind Human Labels Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the tooling for MP1's Step 3, human labels (plan §7 Step 3, §9 B6: "≥20 blind human labels"). The tooling covers five parts: an immutable, seeded and blind labeling selection drawn from frozen cohorts; an append-only label ledger with explicit supersession, a rubric pin and a gate on the rubric's status; an interactive labeling command that only Chad runs; a frozen human reference for B7's calibration; and the `Judgment` shape B7's judge will return. No label is entered, and no model is called, by this plan or its tests. B6's acceptance (≥20 labels) is met only when Chad has labeled in his own terminal.

**Architecture:** Port `evaluation_schemas`, `assessment`, `labels`, `human_reference` and the assessment and labeling commands of `evaluation_cli` from the earlier repository (PORTING-MAP §3.3, §3.5, §8 "B5–B6"), as behaviour-tested rewrites. Three changes of design:
1. An assessment draws from one or more frozen cohorts, one per arm. Its selection is seeded, and the items are shown in one shuffled order across arms, under opaque blind ids.
2. What the labeler sees (`queue.json`) is kept apart from what links a blind id to its run and arm (`key.json`). The labeling code never reads the key.
3. A decision may be unresolved. It is recorded and reported, it is never a pass, and the item stays in its denominator.

**Tech Stack:** Python ≥3.12, Pydantic 2, pytest, ruff. No new dependency.

**Spec:** `docs/MP1-BONSAI-HELP-CHATBOT.md` (§6.2, §7 Steps 3–6, §9 B6–B8), `AGENTS.md` (Human labels, No fabrication, Criteria, Pipeline, Public repository rules), `docs/PORTING-MAP.md` (§2, §3.3 rows `evaluation_schemas`, `assessment`, `labels`, `human_reference`, `calibration`; §3.5 row `evaluation_cli`; §4 item 11; §8 B5–B6), `docs/DECISIONS.md` (November 24, 2026: B5 entries, "Open questions for Chad (B5)", "baseline collection (B5)"). The earlier repository `aia-mp1-synthetic-data` is private and read-only. Port its modules and tests by reading them there. Never copy its fixtures, prompts, rubrics, data, owner strings or URLs.

**Inputs that already exist (read-only for this plan):** collection `baseline-2026-11-24-r2` (ready) and cohort `baseline-b5-cohort-1` (50 items, 10 per category, assessed split, generator v1.1), both under the git-ignored `runs/`. Also `config/rubric.json`, `bonsai-rubric-v1`. ## Global Constraints

- **Only Chad enters labels.** An assistant never enters, edits, imports or fabricates a human label. It never runs `label` or `freeze-human-reference` interactively or through a pseudo-terminal, and it never writes a label file under `runs/` or `data/`. Tests write synthetic labels for synthetic assessments under `tmp_path` only, and every test reviewer string is visibly synthetic (`"synthetic-reviewer"`).
- **Labeling refuses while the rubric is not `chad_accepted`.** The refusal comes before any item is shown. Only a dated `DECISIONS.md` entry in Chad's own words can make the rubric `chad_accepted` (B5), and an assistant never sets that status. Test rubrics with status `chad_accepted` are written only under `tmp_path`, with a review record whose `words` read `"synthetic test acceptance, not Chad's"`.
- **Labeling is blind.** The display shows the item's seven fields, its category, its setup record, the model's quotes (each with the cited section it names) and the full text of its cited sections, and nothing else (Chad, November 24, 2026: "Show category and quotes"). It never shows the run id, item id, arm, prompt variant, prompt hash, model, generation time, collection or cohort id, gate results, judge output or any other label.
- **Labels are append-only.** A correction is a new record with an explicit `supersedes_label_id`. An interrupted write is detected and reported, and the files are left for inspection, never repaired. A leftover lock is reported and never deleted by code.
- **What each label carries:** the trace id, a UTC timestamp, the pinned rubric version and SHA-256, and a decision per dimension of `0`, `1` or `null` (unresolved). Unresolved is reported, never counted as a pass, and the item stays in its denominator (`AGENTS.md`, "A missing judgment is unresolved, not a pass"; rubric labeling rule 4). Free-text notes stay in the local ledger; they never enter Git, and the B10 exporter drops them.
- **Immutability.** Assessments, label checkpoints and human references are never overwritten. Every new selection gets a new assessment id. Cohorts, collections and runs are read, never written.
- **Thresholds come from the pinned rubric.** That covers 20 blind labels per arm (`thresholds.blind_labels.minimum_per_arm`), the dimension ids and the label values. Nothing is hard-coded a second time.
- **Local evidence only.** Assessments live under `runs/assessments/` (git-ignored) or a path outside the repository. Messages name files, never absolute paths. Nothing here calls a model endpoint.
- **Tests exercise behaviour.** Synthetic cohorts are built in `tmp_path` with the existing fake transports (`tests/fakes.py`), and documentation text comes only from the committed fixture slice. No skip, xfail, TODO or stub.
- **Verification for every task:** `uv lock --check`, `uv run --locked pytest -q`, `uv run --locked ruff check .`, `uv run --locked ruff format --check .`.
- **No commit or staging in this workflow.** Commits happen only when Chad asks; the "commit" lines below name the intended message for that time.

## What "blind" means in B6 (resolving the tension)

Plan §7 Step 3 asks Chad to label "without knowing which run they came from". Plan §7 Step 6 puts Phase A (judge calibration on the baseline items) before Phase B, and Phase B creates the corrected run. When B6 labels, then, only the baseline arm exists. In B6 Chad cannot be blind to the arm at the level of the whole set: he knows every B6 item is a baseline item. The judge's v2 examples also need labeled items from the development split (Chad's B5 decision "Assessed split (Recommended)"), and those items do not exist yet.

The plan therefore separates two kinds of blindness and records the split as an assistant's call (Decision 1):

1. **Per-item blindness (B6, always).** Each item is shown under an opaque blind id (`L-001`, …), in one seeded shuffled order. The display holds only the allowed fields (above). `label-status` and `assessment status` show totals and blind ids, never a count per arm. The labeling code never reads the key that links a blind id to its run and arm. No judge output exists yet: B7's judge refuses to run on an assessed selection whose human reference is not frozen (an interface obligation for B7, Task 4).
2. **Arm blindness (B8).** This is the comparison the plan's sentence protects. B8 creates one blind mixed-arm assessment: the corrected cohort's items plus baseline cohort items that no earlier assessment selected (`--exclude-assessment`). Both are shuffled into one queue, so Chad cannot tell an item's arm. Cohort `baseline-b5-cohort-1` has 50 items, so B6 can label up to 30 and still leave the 20 that B8 needs.
3. **Development labels (for judge v2).** These come from a separate `development` assessment, drawn from a development-split cohort. It is never mixed with an arm assessment, and its labels never enter an arm's denominator or the Phase A agreement. It can be created whenever a development cohort exists; the tooling is the same.

Whether B6's baseline labels or B8's mixed-queue baseline labels give the baseline figure for the improvement ratio is Chad's call (Open question 3). The tooling supports either.

## Decisions this plan makes (assistant's calls, recorded in DECISIONS.md in Task 7)

1. **Blindness as above.** In B6 items are blind one by one; arm blindness for the comparison comes from B8's mixed queue of corrected items and baseline items not yet labeled. Development labels live in their own assessment kind.
2. **Assessment sources.** An assessment draws only from frozen cohorts (`cohort.load_cohort`, which re-verifies the collection evidence), with one cohort per arm. The arm is derived from the cohort's collection identity, never typed by the operator:
   - The collection's `purpose` is `baseline` or `corrected`, and it must equal `prompt_variant`. `smoke` is refused.
   - Split `assessed` makes an `arm` source. Split `development` makes a `development` source.
   - An assessment is all `arm` sources (kind `arm`) or all `development` sources (kind `development`); a mix is refused.
3. **Seeded selection.** Algorithm `sha256-stratified-v2`, run per source:
   - Leave out the item ids that the listed `--exclude-assessment` assessments selected.
   - In each category, sort the remaining items by `sha256(seed, cohort_id, item_id)` and take `count / 5`.
   - `count` is per source and a multiple of 5. For kind `arm` it is at least the rubric's `thresholds.blind_labels.minimum_per_arm` (20). For kind `development` it is at least 5.
   - A shortfall in any category is refused, never padded.
4. **Blind display order and ids.** The selected items of all sources are put into one order by `sha256(seed, "order", trace_id)`. Blind ids `L-001` … `L-NNN` are given by position in that order, so a blind id carries no source information.
5. **Queue and key kept apart.** `queue.json` holds, per blind id, only what the display and the label pins need: `blind_id`, `trace_id`, `payload_sha256`, the seven-field `item`, the display setup record and the cited `CitedSection` references. `key.json` maps each blind id to `source_index`, `item_id`, `run_id` and `arm`. The manifest seals both by SHA-256. `labels` and the label display never import or call the key loader; only `human_reference` (after labeling) and B7+ stages read it.
6. **What the display shows.** It shows the item's seven fields and a setup record: Blender version, Bonsai version, IFC schema, discipline and model state, rendered from `reference/setup-profiles.json` at create time. The setup id, split, status and review fields are left out. It also shows each cited section's source, path, heading and full text, re-derived from the hash-verified fixture slice by `sampler.section_texts`.
   - **Changed by Chad on November 24, 2026 ("Show category and quotes"):** the display also shows the item's category and the model's quotes, each quote with the section id it names (as stored in the envelope, quote text as the model wrote it). Any offered section the item did not cite is still not shown. Both fields are part of the assessment's display format and hash from the first assessment on.
   - Control characters other than newline and tab, in item text or section text, are shown escaped, so a model reply cannot drive Chad's terminal.
7. **Rubric pin and gate.** `assessment create` refuses unless the rubric is `chad_accepted`. It stores a copy as `rubric.json` and pins `rubric_version` and `rubric_sha256` (`rubric.rubric_sha256`). `label` refuses before showing anything if any of these hold:
   - the stored copy's hash differs from the pin;
   - the pinned rubric is not `chad_accepted`;
   - the repository's current `config/rubric.json` has another hash.

   In the last case the message is "rubric changed since the assessment was created; create a new assessment".
8. **Decision values.** `Decisions` has all six keys, each required and explicit, with the value `0`, `1` or `null`. Booleans, floats and strings are refused. The judge's `DimensionJudgment` allows only `0` or `1`, with a non-blank `reason`. A judge that cannot decide has a failed or missing attempt, which B7 reports as unresolved; it never has a `null` decision.
9. **Interactive entry only.** `label` and `freeze-human-reference` refuse unless both stdin and stdout are terminals, and the refusal comes before anything else is printed. Neither has a flag or environment variable that bypasses the check, and neither has a non-interactive "decisions on the command line" mode (the old `--item-id/--decisions` path is not ported). Each session starts with a typed confirmation, `label <assessment_id>` or `freeze <assessment_id>`, after a line saying that the decisions are recorded as the reviewer's own. Like `gold packet import`, a pseudo-terminal would pass the check. That an assistant never uses one is a process rule in `AGENTS.md`, which code cannot enforce.
10. **Per-item entry.**
    - For each dimension: `0`, `1`, `u` (unresolved), `?` (shows that dimension's labeling notes) or `q` (quit).
    - After six answers the summary is shown, then `save? [y/redo/q]`. A note is optional and stays local.
    - Nothing is written until `y`. Quit, EOF or Ctrl-C mid-item writes nothing for that item. There is no skip, because rubric rule 4 says "an item is never skipped".
11. **Ledger layout.** `labels.jsonl` holds hash-chained envelopes `{label, previous_sha256, sha256}`. `labels-checkpoint.json` holds `{assessment_sha256, ledger_sha256, count}` and is written atomically after each append. `.labels.lock` is an exclusive writer lock. `assessment create` writes no label file; the first saved label creates the ledger and then the checkpoint. That gives four states:
    - neither file → no labels yet;
    - ledger without checkpoint → first write interrupted;
    - checkpoint without ledger → evidence missing;
    - hash or count mismatch → interrupted or edited.

    The last three are refused with "preserve and inspect".
12. **Supersession.** `label --amend L-NNN --supersedes LABEL_ID` shows the item again without its earlier decisions, and records a new label whose `supersedes_label_id` must equal the current effective label id for that blind id. Before the human reference is frozen an amendment keeps `review_stage: "blind"`. After the freeze it is `post_review` and never changes the frozen reference.
13. **Freezing the human reference.** `freeze_reference` needs all of the following:
    - an interactive declaration (`--declare-blind` plus the typed confirmation);
    - an effective label for every selected blind id, all `blind`, all from the declaring reviewer;
    - at least the rubric's per-arm minimum for each arm (kind `arm`);
    - an unchanged rubric pin;
    - no judge evidence under the assessment.

    It writes `human-reference.json` once: the effective labels, the ledger prefix's SHA-256 and line count, counts per arm (read from the key now that labeling is complete), unresolved counts per dimension and per arm, the kind, and the pins. Unresolved decisions do not block a freeze; they are reported and stay in the denominators.
14. **Assessment ids.** The CLI accepts any safe id (`tracing.run_directory` rules). README advises neutral ids for mixed assessments (`b8-blind-1`, not `corrected-…`), because Chad types the id.

## Review Focus

1. A display path that leaks the arm. The synthetic cohorts use sentinel run ids, model names, prompt hashes and collection and cohort ids. The output of `label` (each item), `label-status` and `assessment status` must contain none of them, and none of the item ids or `generated_at` values. (Task 3 test `test_display_never_shows_provenance_sentinels`; Task 5 test `test_status_commands_never_reveal_arm_or_item_ids`.)
2. A rubric that is `assistant_drafted`, or changed after the assessment was created, means no item text is printed and no label file is created. (Task 2 test `test_create_refuses_unaccepted_rubric`; Task 3 test `test_label_refuses_rubric_not_accepted_or_changed`.)
3. Non-interactive stdin means exit 2 before anything is shown, with no flag or environment escape. (Task 5 tests `test_label_refuses_non_interactive_stdin`, `test_no_flag_or_env_bypasses_the_terminal_check`.)
4. A crash between the ledger append and the checkpoint means that `label`, `label-status` and `freeze-human-reference` all refuse, and every file's bytes are unchanged. (Task 3 test `test_interrupted_append_is_detected_not_repaired`.)
5. An unresolved dimension is never a pass and never removes the item. It appears in `label-status` totals and in the frozen reference's unresolved counts, and `rubric.overall_pass` returns `None` or `False`, never `True`. (Task 1 test `test_unresolved_is_never_a_pass`; Task 4 test `test_reference_reports_unresolved_and_keeps_denominator`.)
6. B8's mixed-arm assessment that excludes B6's selection shares no item with it, interleaves both arms, and refuses when too few unselected baseline items remain. (Task 2 tests `test_exclusion_gives_disjoint_selection`, `test_mixed_arms_are_interleaved_by_seed`.)

### Task 4: Human reference

**Files:**
- Create: `src/bonsai_help/human_reference.py`
- Test: `tests/test_human_reference.py`

**Interfaces:**
- Consumes: `assessment` (`load_assessment`, `load_key`), `labels.load_labels`, `labels.check_rubric_gate`, `rubric`, `tracing`.
- Produces:
  - `HumanReferenceError(ValueError)` (built under this name, because `ReferenceError` would shadow Python's built-in).
